# Принципы проверки качества

Правила обязательны для любой документации BMAD, по которой планируется генерация кода.

## П1. Сначала скрипт, затем LLM, затем человек

Если проверку можно выразить скриптом, LLM для неё не используется. LLM получает только то, что скрипт не может решить. Человек получает только находки, требующие суждения.

## П2. Гейт ищет дефекты, а не доказывает полноту

Прогоны показали, что разные запуски находят разные проблемы. Зелёный LLM-гейт значит «проблем этого вида не найдено», а не «документ полный». Никто не пишет «документация полная» на основании одного LLM-гейта.

## П3. Автор не выставляет себе вердикт

Вердикт PASS выносит тот, кто не писал документ: чистый контекст LLM без контекста автора и человек на воротах. Самопроверка автора вердиктом не считается.

## П4. Чистый контекст и узкий пакет

LLM-гейт запускается через `tools/run_gate.py`: без инструментов, настроек, памяти и MCP. Вход собирается `tools/build_packet.py`. Обычный агент для гейта запрещён, он добавляет около 32 тысяч токенов на запуск.

## П5. Каждая находка проверяема

Находка содержит цитату, что отсутствует или неверно, и уровень `blocker` или `minor`. Находка без цитаты отбрасывается. Находки LLM не правят документ автоматически: сначала их просматривает человек, потому что ложные срабатывания неизбежны.

## П6. Бюджет задан заранее

У каждого гейта есть бюджет токенов на запуск. Оценка записывается до запуска. Факт больше оценки в 2 раза и более останавливает работу до выяснения причины. Расход каждого запуска записывается.

## П7. Запуск только на изменённом

Гейт запускается, когда изменился его вход. Повторный запуск без изменений запрещён, кроме калибровки.

## П8. Смоделированное не выдаётся за настоящее

Вымышленные данные, допущения и неисполненные проверки помечаются явно. Отчёт перечисляет, что не запускалось.
